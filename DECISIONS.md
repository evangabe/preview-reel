# DECISIONS.md

Running log of choices, tradeoffs, and assumptions, written as the work happened. Trimmed for submission to the entries worth defending; the unabridged log (~160 entries, including scaffolding minutiae and per-checkpoint validation timings) is kept locally.

Format: `- **[Area]** Chose X over Y because Z. Tradeoff: W.`

---

## Scoping

- **[Problem]** Chose preview-deployment demo recording over a general demo generator because the trigger, the environment, and the audience are all already defined by the PR. Tradeoff: only useful to teams already on Vercel preview deployments.
- **[Build vs buy]** Chose to build on `webreel` (Vercel Labs, Apache-2.0) rather than implement frame capture and encoding. Tradeoff: the project reads as a layer on someone else's tool unless the authoring and trigger work is substantial.
- **[Architecture]** Split exploration from recording: `agent-browser` emits a `webreel` config, `webreel` replays it. Because an agent's live fumbling is unpublishable and a config is reviewable and re-runnable. Tradeoff: two stages, two failure modes, longer runs.
- **[Trigger]** Chose a `[feat]` PR title tag over a `CHANGELOG.md` diff. Deterministic, zero-cost on the common path, and puts the decision with the author. Tradeoff: only fires when someone remembers to tag.
- **[Trigger]** Chose title tags over GitHub labels because labels need repo setup. Tradeoff: pollutes PR titles, and a tag added after the fact only fires on the next deployment.
- **[Identity]** Keyed runs on `(repo, prNumber)` rather than feature slug or deployment ID. PR numbers are stable; titles get edited and deployments repeat per push.
- **[Model]** The model scopes the demo but does not decide whether to record. Removes the false-positive problem entirely rather than tuning for it.
- **[Comment]** One comment updated in place, never the PR description. A bot that overwrites human-authored text loses that fight every time.
- **[Storage]** Blob metadata instead of a database. Tradeoff: cross-run queries for the gallery get awkward; escape hatch is a per-repo index blob, not Postgres.
- **[Scope]** Cut: credential management UI, TTS voiceover, uploaded audio, stale-demo detection, multiple demos per PR, auth. Each is a real feature; none is needed to prove the loop.
- **[Scope]** Hardcoded credentials for v1. The correct answer is a scoped demo account with short-lived credentials via Vercel Connect, which is a day of work and not the interesting part.
- **[Onboarding]** One team-level Vercel webhook plus an env allowlist, instead of per-repo installation. Tradeoff: target projects must live in the same Vercel team; a real product needs a Vercel Integration.
- **[Auth]** Fine-grained PAT over a GitHub App. Tradeoff: single-repo, single-tenant, manual rotation.
- **[Webhook]** Ack within 30s and hand off to the Workflow, because Vercel aborts at 30s and retries non-2xx for up to 24 hours. Delivery order is not guaranteed, so idempotency is a hard requirement rather than a nicety.
- **[Trigger]** ~~Assumed the deployment webhook payload carries enough git metadata to resolve the PR title without a GitHub API call.~~ Checked against Vercel's webhook API docs before writing code: it doesn't — `deployment.meta` carries `githubPrId`, `githubCommitRef`, `githubCommitSha`, not title/body. A GitHub call is required either way; `githubPrId` turns it from a branch search into an exact `GET` by PR number.

## Spec review before building (docs-only pass against current Vercel/webreel/agent-browser docs)

- **[Bug]** Spec originally said filter webhooks on `target: "preview"`. Vercel's actual values are `production`, `staging`, or `null` — preview deployments are `null`. That filter would have silently dropped every event the project exists to process. Caught by reading the webhook API reference, not by testing it live. Fixed to `target !== "production"`.
- **[Credentials]** Spec assumed the bypass secret and login could be injected as HTTP headers/cookies into the recorded flow. `webreel`'s config schema has no header or cookie field. Chose URL query params with `webreel`'s built-in `${VAR}` env-substitution over forking `webreel` or writing a custom replay layer. Tradeoff: the target app needs one new route (`/api/demo-login`) it wouldn't otherwise have.
- **[Auth]** Cut a scripted login step in favor of a server-side token-for-cookie exchange (`/api/demo-login`), resolving what was an open question by design rather than by testing whether session-state injection works. Replaced `TARGET_APP_EMAIL`/`TARGET_APP_PASSWORD` with a single `DEMO_LOGIN_TOKEN`.
- **[Storage]** Spec's status page assumed polling a single Blob object overwritten per stage. Vercel Blob's `cacheControlMaxAge` floor is 60s and overwrites take up to 60s to propagate — a live status page built on that would show a stale stage for most of a 3-minute run. Changed run-status records to append-only per-stage objects, with the Workflow run as fallback, keeping Blob as the durable terminal record rather than the live one.
- **[Idempotency]** Spec's idempotency requirement only covered duplicate deliveries for the same deployment ID, not a second deployment for a PR with a run *in progress* (a push mid-run). Added an in-progress check keyed on `(repo, prNumber)`, separate from the completed-record check.

## Platform setup

- **[Plan]** Team webhooks are Pro/Enterprise only, so the plan is a hard prerequisite — the webhook is the entire trigger. Everything else in the stack (Sandbox, Blob, Workflow, AI Gateway, Protection Bypass) works on Hobby; this one feature forces the upgrade.
- **[Config]** `VERCEL_OIDC_TOKEN` is **not** a runtime environment variable in deployed functions. The spec and `.env.example` both listed it alongside the hand-set secrets, and validating it at boot 500'd every dynamic route in production while `/` (static) kept returning 200 — a failure that only shows up on deploy, not in `npm run build`. Now validated off-platform only. This was my assumption, carried straight from the spec, and the deploy is what caught it.
- **[Config]** Validate env in `instrumentation.ts` (runtime boot) rather than at build. The spec said "fail the deploy", but the webhook secret cannot exist before the first deploy — a build-time check makes the first deploy structurally impossible. Tradeoff: a missing secret 500s every dynamic route instead of failing the build.
- **[Storage]** Created the Blob store with `--access public`. Public-read via unguessable URL is the stated tradeoff, and the PR comment embeds a poster that GitHub's image proxy fetches unauthenticated. Tradeoff: the privacy punt is now a property of the store, not just the code.
- **[Access]** Preview Reel's own production alias is public, while deployment-specific URLs sit behind Vercel Authentication. The webhook must target the alias — pointing it at a deployment URL would auth-wall Vercel's own delivery service. Same protection asymmetry the target project relies on in reverse.
- **[Links]** Chose an explicit `APP_BASE_URL` over Vercel's injected production-host variable because the latter was unavailable inside a Workflow step and caused PR comments to link to localhost.

## Live verification against the target (before any pipeline code)

- **[Trigger]** Confirmed against the target project's real deployments: the PR preview arrives with `target: null` and `meta.githubPrId: "1"`. The `target !== "production"` filter and `githubPrId` fast path are verified, not assumed.
- **[Access]** The auth wall has a fingerprint: a wrong or missing bypass secret 302s to `vercel.com/sso-api?…`, while a correct secret against an unauthenticated app 302s to same-origin `/login`. "Detect the auth wall explicitly" is therefore a host check on the redirect target. Two different failure reasons, cheaply distinguishable.
- **[Access]** The query-param form (`?x-vercel-protection-bypass=…&x-vercel-set-bypass-cookie=true`) answers 307 to the clean URL and sets `_vercel_jwt`. So `webreel`'s first navigation carries the secret exactly once and every subsequent step is cookie-authenticated with a clean address bar. WebReel also captures only the viewport, never the address bar, so the secret cannot appear in a frame.
- **[Auth]** Resolved the login open question by running it: a fresh cookie-less context hitting `/api/demo-login?token=…&next=/` plus the bypass params lands on `/` with 200 after two redirects. A wrong token yields 401 at `/api/demo-login`. Login failure and auth-wall failure are distinct status codes on distinct hosts.
- **[Recording]** Inspected `webreel@0.1.4` rather than trusting the docs: `${VAR}` substitution leaves unset variables as literal text, so a missing env var at replay produces "Element not found", not a clear error. The runner asserts the substitution variables are present before invoking `webreel record`.
- **[Exploration]** `agent-browser` followed the demo-login redirects and retained both cookies, but `open --headers …` followed by commands without that option restarted Chrome at `about:blank`. `set headers` once before `open` preserves the session; the explorer uses the persistent setting.

## Sandbox runner

- **[Validation]** Mirrored WebReel's action union in zod but deliberately narrowed model-produced navigation to same-origin paths, typing to stable selectors, one target per action, one video, and ≤12 steps. Tradeoff: valid hand-authored WebReel configs may fail Preview Reel's stricter schema; this validates what the model may emit, not everything WebReel can execute.
- **[Exploration]** The model returns only `{ found, reason, steps }`; runner code constructs the auth URL, base URL, viewport, output, and thumbnail. Letting the model repeat credential placeholders creates risk without adding judgment.
- **[Privacy]** Explorer transcripts log every browser tool call and model step but redact all three credentials before writing.
- **[Failure]** Added `record-failed` and `explore/model-call-failed` as honest fallback reasons beyond the plan's closed taxonomy. Mapping an unknown recorder failure to `navigation-failed` or a Gateway/account failure to `invalid-config` would be specific-sounding but false.
- **[Sandbox]** Replaced the plan's `runtime: "node24"` with the explicit `vercel/sandbox/universal:latest` image after the live runtime booted Amazon Linux 2023 despite the SDK README describing Ubuntu.
- **[Recording]** WebReel 0.1.4's lazy ffmpeg URL is dead (its pinned BtbN 7.1 asset 404s). The snapshot installs a static ffmpeg 8.1 and sets `FFMPEG_PATH`, removing that network dependency. Tradeoff: the snapshot script owns a binary URL until WebReel fixes its installer.
- **[Recording]** WebReel's recording path ignores `CHROME_PATH` and unconditionally downloads its own headless shell, so the snapshot contains two Chromes (~190 MB extra). Avoiding it would require forking WebReel, which is not justified here.
- **[Recording]** Patched the snapshotted WebReel runtime in two version-checked places: remove Linux's `--enable-begin-frame-control` (screenshots never resolve in Sandbox without it), and surface ffmpeg stderr instead of a later `rename ENOENT`. Tradeoff: snapshot construction intentionally fails when an upstream release changes either source string, forcing the workaround to be reviewed.
- **[Snapshot]** The model-authored smoke recording was initially too short and read the wrong output path; zero captured frames exposed the ffmpeg error. The final 3-second, two-step smoke runs at the end of every snapshot build so a broken snapshot fails at build time, not mid-demo.
- **[Storage]** Uploads are immutable and retry-safe: `head()` returns an existing object, `put()` uses `allowOverwrite: false`, and a second `head()` resolves the race where another retry wins between those calls. Tradeoff: a bad first write cannot be corrected in place; a re-run needs a new run identity, which matches the append-only model.

## Trigger and orchestration

- **[Trigger]** Moved the tag check from a Workflow step into the webhook handler. The handler already makes the one GitHub call that returns the title, so an untagged PR creates no Workflow run and no Blob object of any kind.
- **[Idempotency]** The deployment sentinel is claimed last, immediately before `start()`, using Blob's `allowOverwrite: false` as the only conditional-write primitive. Filters and the GitHub call run first so a transient GitHub failure never permanently burns a deployment. Workflow SDK's `start()` has no idempotency-key option, so this is the mechanism.
- **[Identity]** The Workflow run ID is the run ID; no separate UUID or mapping. Tradeoff: the in-progress pointer can only be written after `start()`, leaving a sub-second double-start window. Accepted; the deployment sentinel still forbids duplicate runs per deployment, and a 15-minute staleness guard on pointers prevents a stuck run from locking a PR out forever.
- **[Workflow]** Provision → explore → record → upload is one step with `maxRetries = 0` that returns `{ ok, failure }` instead of throwing, because Workflow retries cannot tell `provision/create-failed` (retry once) from `explore/preview-protected` (never retry), and Sandbox handles and mp4 buffers must not enter the serialized event log. The single provision retry lives inside `provisionSandbox()`.
- **[Security]** The wrong-bypass probe exposed that WebReel's `element-not-found` detail includes its resolved URL, so the first failure event briefly contained replay credentials. Deleted the objects, then centralized redaction at the Sandbox boundary and verified the replacement event contains `<redacted>` and none of the three secrets.
- **[Exploration]** Added the first 10,000 characters of the PR body as delimited, explicitly untrusted explorer context, because the target's discoverability instructions live there. Tradeoff: long bodies are truncated and still consume model context.
- **[Exploration]** The model found and exercised PR #2 correctly but repeatedly emitted agent-browser `press`/`fill` names instead of WebReel `key`/`type`, then discovered that a no-op click passed the broad union schema. Added exact replay examples and made the second invalid finish terminal. Tradeoff: schema repair gets one retry, as specified.
- **[Model]** Made `openai/gpt-5.6-luna` with medium reasoning the shared default for scoping and exploration after a live scoping call returned a valid spec in 4.9s. One centralized constant keeps a future measured downgrade simple.
- **[Scope]** Replaced the title-only fallback with an AI Gateway JSON call over PR title/body, changed paths, and preview URL; zod validates without coercion, one malformed response gets one repair call, and a second failure records `scope/invalid-output`. Tradeoff: failed scoping stores a run with `demo: null` because inventing a fallback spec would violate the no-default rule.
- **[Privacy]** Disabled Gateway's ZDR requirement for Luna after the live call proved the allowlisted OpenAI route has no ZDR-attested credentials; accepted standard provider retention for this public-repo demo. Tradeoff: private-repo support must restore ZDR before launch.

## UI and API

- **[Storage]** Audit found a manual re-run against the same deployment would hit `putOnce`'s existing `config.json`/`video.mp4` and return the *old* artifacts as if freshly written. Nested demo artifacts under `{deploymentId}/{runId}/` rather than enabling `allowOverwrite`, which would put a rewritten poster behind the 60s CDN cache. Tradeoff: the gallery dedupes to the newest metadata per `(repo, prNumber)`.
- **[Rerun]** The re-run route is public like the rest of the app and deliberately skips the completed-demo and deployment-sentinel guards — those stop *automatic* re-recording; this is the manual path. It keeps the in-progress guard so a PR never has two concurrent runs. Tradeoff: an unauthenticated full re-run spends model budget; the Gateway spend cap is the backstop.
- **[Cost]** A live Luna probe disproved the planned generation lookup: AI SDK's response ID is `aitxt-…`, the actual `gen_…` ID lives in `providerMetadata.gateway.generationId`, and `getGenerationInfo()` still failed with that ID after 4.25s. Both call sites now read the immediately available `providerMetadata.gateway.cost`. Costs are never estimated.
- **[Planning]** Reverted the in-progress guard extraction because its second caller (the rerun route) did not exist yet, violating the no-speculative-abstraction rule. The initial diagnosis that the new `workflow/api` import caused the smoke script to hang was also wrong: `npx tsx` stayed slow after the revert, while the local `tsx` binary ran immediately.
- **[Gallery]** Replaced poster cards with grouped tables because the gallery needs faster visual scanning across demos. Tradeoff: the poster is compact; the title links to the run while the PR cell links to GitHub.
- **[Run status]** Derive terminal status from append-only events before consulting Workflow; local development also trusts in-progress events because a local Workflow runtime cannot resolve production run IDs and left the page request open for minutes. Tradeoff: an unexpected local Workflow crash can leave a development-only run shown as in progress.
- **[UI]** Pinned the app to shadcn's `.dark` token set. A toggle is out of scope, and `prefers-color-scheme` would make preview screenshots depend on the reviewer's OS. Tradeoff: no light mode.
- **[UI]** Step labels are a lookup over the twelve WebReel actions with a verbatim fallback, instead of validating steps with the model-output schema. The schema constrains what the model may emit; the UI must render whatever the runner actually saved. Tradeoff: an unknown action gets a raw label, never an error.

## Demo readiness

- **[Planning]** With a day left, chose four items from the assessment rubric over polish: the rerun route (the on-stage "watch it run" moment and the promise the failed-state comment already makes), placeholders as a visible feature, an explicit auth-wall reason in the record path, and model/cost visibility. Cut stale-demo detection to a carry-forward list.
- **[Process]** Each slice ships as its own PR, validated on the Vercel preview build (API via `vercel curl`, UI on production after merge), and merged before the next branches from `main`.
- **[Rerun]** Extracted the webhook's in-progress guard into `lib/runs/in-progress.ts` now that the rerun route is its second caller; it returns the active `runId` rather than a boolean so the route can point a 409 at the running run.
- **[Rerun]** Order of checks is 404 → 400 → 409 in-progress → 409 no-config → start, and the index write after `start()` is reported as `202 { runId }` even if the pointer write fails: the run is already going, and hiding it behind a 5xx would invite a second click.
- **[Validation]** The first preview re-run failed at `record` from env drift, not code: `DEMO_LOGIN_TOKEN` had been rotated by updating the shared entry, but a stale Preview-only entry shadowed it. Deleted it. Tradeoff: one wasted run with a misleading `navigation-failed` reason — exactly the gap the auth preflight closes.
- **[Auth wall]** Probed the target with curl before writing the preflight: a wrong bypass gets `302 → vercel.com/sso-api`; a wrong login token gets a **401 from `/api/demo-login`** after Vercel's cookie hop, not a redirect to `/login` (the spec's assumption was false). The good path is `307` → `302 /` → `200`, so the preflight must carry cookies across hops or it lands on the SSO wall and misreports `preview-protected`.
- **[Runner]** Auth-wall detection in the record path is a preflight, not output parsing: before `webreel record`, the entry URL is substituted in memory and its redirect chain followed manually (≤5 hops, cookie jar). Classification is a pure function with a unit test pinned to the observed hops. A preflight network error is logged and the run continues — the preflight sharpens a reason, it must not add a new way to fail.
- **[Runner]** Rule set: 3xx to `vercel.com` → `preview-protected`; 401/403 from `/api/demo-login` → `login-failed`; any other 401/403 → `preview-protected`; same-origin 3xx to `/login` → `login-failed`; everything else proceeds.
- **[Storage]** `metadata.json` gains `model: { id, reasoningEffort } | null`, read with `.nullable().default(null)` so objects written before the field still list and render "not recorded". This is storage-schema evolution, not model-output coercion; "never coerce or default" stays absolute for zod on model output. A test pins that `.default` does not loosen `.strict()`.
- **[UI]** The Steps tab shows each video's entry URL with every `${VAR}` token rendered as a `<mark>`, plus one caption stating that credentials are substituted at replay time and never written to the file. This makes the rule the validator enforces legible instead of incidental.
- **[Runner]** The first full-pipeline recovery run for PR #1 failed at `explore` with `invalid-config: Expected double-quoted property name in JSON` — not an auth reason. Root cause was two-fold: (1) PR #1's preview was built before the token rotation, so it 401s the current token (Vercel bakes env into a deployment); (2) the transcript redactor's regex `[^"&\s]+` ate the backslash of an escaped quote when the token was the last query param inside a nested JSON string, so the first log write threw and masked the login failure. Fixed the regex with a test pinned to that event shape, and taught the explore path that a browser parked on `/api/demo-login` is `login-failed`.
- **[Runner]** Treat a standard Next.js 404 at the model-scoped entry point as a stale scope, recover at `/`, and use `/` in the replay URL too. This fixes the observed split where exploration navigated from `/inventory` to `/` but WebReel still restarted at `/inventory`. Tradeoff: assumes the target's root route is a valid landing page.
- **[UI]** Replaced the gallery's text metrics with two KPI cards — total reels and reported model spend, each with a past-24-hour trend — over the newest reel per PR. Unknown spend stays `not reported` rather than estimated.
